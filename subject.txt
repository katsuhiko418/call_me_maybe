## V.1 概要

このプロジェクトでは、自然言語のプロンプトを構造化された関数呼び出しへ変換するツールを作成します。

たとえば「40と2の合計はいくつですか？」という質問に対して、`42` を返すのではなく、次の情報を出力してください。

- 関数名：`fn_add_numbers`
- 引数：`{"a": 40, "b": 2}`

実装には **制約付きデコーディング（constrained decoding）**を使用し、出力が100%有効なJSONになることを保証してください。これにより、パラメーター数が0.6B（6億）の小さなモデルでも、ほぼ完全な信頼性を確保します。

## V.2 入力ファイル

プログラムは、`data/input/` ディレクトリにある2つの入力ファイルを処理します。

**`function_calling_tests.json`**

システムが処理すべき自然言語のプロンプトを、JSON配列として格納したファイルです。

例：

```json
[
  {
    "prompt": "What is the sum of 2 and 3?"
  },
  {
    "prompt": "What is the sum of 265 and 345?"
  },
  {
    "prompt": "Greet shrek"
  },
  {
    "prompt": "Greet john"
  },
  {
    "prompt": "Reverse the string 'hello'"
  },
  ...
]
```

それぞれのプロンプトは、「2と3の合計はいくつですか？」「265と345の合計はいくつですか？」「shrekに挨拶して」「johnに挨拶して」「文字列 `'hello'` を逆順にして」という意味です。

**`functions_definition.json`**

システムが呼び出せる関数を格納したファイルです。各関数には、次の情報が含まれます。

- 関数名
- 引数の名前と型
- 戻り値の型
- 説明

例：

```json
[
  {
    "name": "fn_add_numbers",
    "description": "Add two numbers together and return their sum.",
    "parameters": {
      "a": {
        "type": "number"
      },
      "b": {
        "type": "number"
      }
    },
    "returns": {
      "type": "number"
    }
  },
  {
    "name": "fn_greet",
    "description": "Generate a greeting message for a person by name.",
    "parameters": {
      "name": {
        "type": "string"
      }
    },
    "returns": {
      "type": "string"
    }
  },
  {
    "name": "fn_reverse_string",
    "description": "Reverse a string and return the reversed result.",
    "parameters": {
      "s": {
        "type": "string"
      }
    },
    "returns": {
      "type": "string"
    }
  },
  ...
]
```

各関数の説明は、順に「2つの数を足し、その合計を返す」「名前を指定して、その人への挨拶メッセージを生成する」「文字列を逆順にし、その結果を返す」という意味です。

これらの例は、想定される複雑さの目安を示しています。ただし、実際のテストでは、**異なるプロンプトや関数の組み合わせ**が使用されます。

入力ファイルには不正なJSONが含まれている場合や、ファイル自体が存在しない場合もあるため、適切なJSONエラー処理を実装してください。

※上の例の `...` は原文の省略表記であり、実際のJSONでは使用できません。

## V.3 LLMとのやり取り

### V.3.1 LLM SDK

このプロジェクトには、LLMとやり取りするために使用できるラッパークラス `Small_LLM_Model` が、`llm_sdk` パッケージとして付属しています。

SDKには、以下の主要なメソッドがあります。

- **`get_logits_from_input_ids(input_ids: List[int]) -> List[float]`**  
  トークンIDのリストを受け取り、LLMが生成したロジットを返します。

- **`get_path_to_vocab_file() -> str`**  
  トークンIDとトークンの対応関係が記載された、語彙ファイルへのパスを返します。

- **`encode(text: str) -> Tensor`**  
  モデルのトークナイザーを使って、文字列をトークンIDのテンソルに変換します。

- **`decode(token_ids: List[int]) -> str`（任意）**  
  トークンIDのリストを文字列に戻します。このメソッドの使用は任意です。

### V.3.2 生成パイプライン

LLMによる生成処理は、次の手順で進みます。

1. **プロンプト**  
   自然言語で書かれた質問です。  
   例：`"What is the sum of 2 and 3?"`（2と3の合計はいくつですか？）

2. **トークン化**  
   テキストを、サブワード単位の「トークン」に分割します。単純に単語ごとに分ける処理とは異なり、トークナイザーは先頭の空白や句読点を扱い、BPEやSentencePieceなどのアルゴリズムを使って、単語をさらに小さな構成要素に分割することがあります。

   実際に近い例：

   ```text
   ["What", "Ġis", "Ġthe", "Ġsum", "Ġof", "Ġ2", "Ġand", "Ġ3", "?"]
   ```

   `Ġ` は、その前に空白があることを示します。実際のトークナイザーは、テキストを正確に復元できるよう、このような細部も保持します。

3. **入力ID**  
   トークンを、モデルが理解できる数値IDに変換します。

   説明用の例：

   ```text
   [892, 318, 262, 4771, 286, 16, 290, 17, 30]
   ```

4. **LLMによる処理**  
   モデルが、これらの数値をニューラルネットワークで処理します。

5. **ロジット**  
   モデルは、次のトークンとして考えられる各候補に対して、確率に関するスコアを出力します。

   例：

   ```text
   token_5: 0.001, token_42: 0.85, token_100: 0.02, ...
   ```

6. **トークンの選択**  
   これらの確率に基づいて次のトークンを選びます。通常は、最もスコアの高いものを選択します。

   この段階で**制約付きデコーディング**などの手法を適用すると、選べるトークンを制限し、出力が特定の構造に従うようにできます。たとえば、100%有効なJSONを生成するように制約できます。

**重要：** この処理は、トークンごとに繰り返されます。生成したトークンをプロンプトに追加し、応答全体が完成するまで手順2〜6を繰り返します。

簡略化すると、次の流れになります。

```text
プロンプト → トークン化 → 入力ID → LLM → ロジット → 次のトークンの選択
```

### V.3.3 制約付きデコーディングを理解する

言語モデルは、1トークンずつテキストを生成します。各ステップで、モデルは次のトークンとして考えられるすべての候補について、確率分布（ロジット）を生成します。通常は、その分布からサンプリングするか、最も確率の高いトークンを選びます。

制約付きデコーディングは、**トークンを選ぶ前にロジットを変更する**ことで、この処理に介入します。

1. モデルが、すべての候補トークンに対するロジットを生成します。
2. 有効なJSON構造を維持し、かつ期待されるスキーマにも適合するトークンを特定します。
3. 無効なトークン、つまりスキーマや構造を壊すトークンのロジットを、**負の無限大**に設定します。
4. 残った有効なトークンだけを対象にサンプリングします。

このプロジェクトでは、構文上有効なJSONを生成するだけでなく、**特定のスキーマに従わせること**も必要です。

たとえば、`functions_definition.json` であるフィールドが数値に制約されている場合、デコーダーは整数または浮動小数点数として成立する値だけが選ばれるよう、トークンの選択を制限します。これにより、JSONの妥当性とスキーマへの適合性の両方を維持します。

生成される各トークンが、構造上・意味上の妥当性を保ち、必要なスキーマに従うことを保証します。その結果、生成されたJSONからは必ずデータを取り出すことができ、常にエラーなくパースできます。

**プロンプトを与えるだけで、モデルが自発的に正しいJSONを出力してくれることに依存してはいけません。** 関数定義をプロンプトに含め、構造化された出力を期待するだけでは信頼性がなく、この課題で身に付けてほしい技能でもありません。

語彙JSONファイルを使って、トークンとその文字列表現をどう対応付けるかを考えてください。これは、生成の各段階でどのトークンが有効かを判定するうえで極めて重要です。

## V.4 出力ファイルの形式

プログラムは、次の単一のJSONファイルを生成します。

```text
data/output/function_calling_results.json
```

各プロンプトについて、JSONオブジェクトをこのファイルに追加してください。配列内の各オブジェクトには、**以下のキーだけを、過不足なく**含める必要があります。

- **`prompt`（文字列）**：元の自然言語のリクエスト
- **`name`（文字列）**：呼び出す関数の名前
- **`parameters`（オブジェクト）**：正しい型で指定された、必要なすべての引数

### V.4.1 出力例

```json
[
  {
    "prompt": "What is the sum of 2 and 3?",
    "name": "fn_add_numbers",
    "parameters": {"a": 2.0, "b": 3.0}
  },
  {
    "prompt": "Reverse the string 'hello'",
    "name": "fn_reverse_string",
    "parameters": {"s": "hello"}
  }
]
```

### V.4.2 検証ルール

- ファイルは有効なJSONでなければなりません。末尾のカンマやコメントは認められません。
- キーと型は、`functions_definition.json` のスキーマと完全に一致する必要があります。
- 出力のどこにも、余分なキーや説明文を含めてはいけません。
- 必須の引数をすべて含める必要があります。
- 引数の型は、関数定義と一致する必要があります（`number`、`string`、`boolean` など）。

**ピアレビューでは、入力ファイルが変更される可能性があります。提示された例に合わせて、解答をハードコードしてはいけません。**

## V.5 性能と信頼性

実装は、次の基準を満たす必要があります。

- **ほぼ完全な精度**：関数の選択と引数の抽出の正解率が90%以上であること。
- **100%有効なJSON**：すべての出力がパース可能で、スキーマに適合していること。
- **妥当な処理速度**：標準的なハードウェアで、すべてのテストプロンプトを5分未満で処理できること。
- **堅牢なエラー処理**：不正な形式の入力、ファイルの欠落、境界ケースに適切に対応すること。

Qwen3-0.6Bモデルのパラメーター数はわずか5億ですが、適切な制約付きデコーディングを使えば、はるかに大きいモデルに匹敵する信頼性を実現できます。これは、単純なモデルサイズの大きさに対する、構造に基づく誘導の有効性を示しています。

※この段落の「5億」は原文どおりです。V.1の「0.6B（6億）」とは表記が一致していません。

## V.6 実装のテスト

正しく動作することを、次の手順で確認してください。

1. 入力ファイルが `data/input/` ディレクトリにあることを確認します。
2. 次のコマンドを実行します。

   ```sh
   uv run python -m src \
     [--functions_definition <関数定義ファイル>] \
     [--input <入力ファイル>] \
     [--output <出力ファイル>]
   ```

   角括弧 `[]` は、省略可能な引数を表します。

3. `output/function_calling_results.json` が作成されたことを確認します。
4. JSONの構造と内容が正しいことを検証します。
5. 関数名と引数の型が、定義と一致することを確認します。

空文字列、大きな数値、特殊文字、誤った型、曖昧なプロンプト、複数の引数を取る関数など、さまざまな境界ケースでテストしてください。

※手順3の出力先は原文どおりですが、V.4では `data/output/function_calling_results.json` と記載されています。
